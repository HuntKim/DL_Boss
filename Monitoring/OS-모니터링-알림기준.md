# OS 모니터링 알림 기준 정의서

> 기준 문서: `Monitoring/BBT-요건`
> 본 문서는 BBT(통보) 등급 체계를 기반으로, OS 영역(CPU/MEM/DISK/File
> System/Ping Fail/Hang/OS 커널 오류)에 대한 **탐지 기준**과 **통보 채널
> 기준**을 구체화한다.

## 1. 목적

- 장애/성능저하 징후를 메트릭·로그 관점에서 어떤 기준으로 탐지할지 정의한다.
- 탐지된 이벤트의 심각도(알림 등급)에 따라 메일/메신저/SMS 중 어떤 채널로,
  얼마나 신속하게 통보할지 정의한다.
- 이후 모니터링 Agent/Collector 설정(임계치, 알림 룰) 및 로그 수집기(grep
  패턴) 구현 시 그대로 참조 가능한 형태로 정리한다.

## 2. 용어 정리

| 용어 | 설명 |
|---|---|
| 알림 등급 (A/B/C/D) | `BBT-요건` 정의. A/B급은 "30분 이내 조치 필요", C/D급은 "긴급하지 않음" |
| 운영등급 (M0~M4) | 서버(호스트) 단위 업무 중요도. M0~M3는 운영/EHS 등 실서비스, M4는 개발/재연/Staging |
| 완전장애형 | 서비스가 즉시 중단되는 유형(예: Host Down, Kernel Panic) |
| 성능저하형 | 서비스는 유지되나 성능/여유자원이 임계치를 벗어난 유형(예: CPU/Mem 사용률) |

## 3. 알림 등급 및 운영등급 매핑 (기존 `BBT-요건` 요약)

### 3.1 알림 등급별 영향도/긴급도

| 알림 등급 | 영향도 | 긴급도 |
|---|---|---|
| A급 | 전체 서비스/라인 영향 | 30분 이내 조치 필요 |
| B급 | 일부 서비스/라인 영향 | 30분 이내 조치 필요 |
| C급 | 전체에 잠재적 영향 | 긴급하지 않음 |
| D급 | 일부에 잠재적 영향 | 긴급하지 않음 |

### 3.2 운영등급 × 장애유형 → 최종 알림 등급

같은 이벤트(예: CPU 80% 초과)라도 **호스트의 운영등급**에 따라 최종 통보
등급이 달라진다.

| 운영등급 | 업무 특성 | 생산 영향도 | 완전장애형 발생 시 | 성능저하형 발생 시 |
|---|---|---|---|---|
| M0 | 운영 | 大 | A/B | C |
| M1 | 운영 | 大 | A/B | C |
| M2 | 설비/품질 분석 운영 | 中 | B | C |
| M3 | EHS 및 공통 서비스 운영 | 中 | B | C |
| M4 | 개발/재연/Staging | 無 | D | D |

> 표는 `BBT-요건`의 "메트릭 기준1"을 장애유형(완전장애형/성능저하형) 축으로
> 재정리한 것이다. 실제 등급 산정 시에는 `BBT-요건`의 "메트릭 기준2"에 정의된
> 메트릭별 기본 등급(A/B/C/D)을 우선 적용하고, M4 호스트는 예외적으로 D급으로
> 강등한다.

## 4. 알림 등급별 통보 채널 기준

| 알림 등급 | 메일 | 메신저 | SMS | 발송 시점 |
|---|---|---|---|---|
| A급 | ✅ | ✅ | ✅ | 탐지 즉시, 시간대 무관 |
| B급 | ✅ | ✅ | ✅ | 탐지 즉시, 시간대 무관 |
| C급 | ✅ | ✅ | ❌ | 탐지 즉시 (SMS는 미발송) |
| D급 | ✅ | ❌ | ❌ | 탐지 즉시 또는 일 1회 요약 발송 |

**적용 원칙**

1. **30분 이내 조치가 필요한 A/B급은 전 채널(메일+메신저+SMS)로 동시 발송**한다.
   담당자가 업무 시간 외이거나 메신저를 확인하지 못하는 상황을 가정해 SMS를
   반드시 포함한다.
2. **C급은 메신저+메일**로 발송해 인지시키되, 즉시 전화/SMS 대응까지는
   요구하지 않는다.
3. **D급은 메일 위주**로 발송하며, 알림 수 과다로 인한 피로도(alert fatigue)를
   낮추기 위해 실시간 발송 대신 **일 1회 요약 리포트** 방식도 병행 가능하다.
4. (권장, 선택 적용) **에스컬레이션**: A/B급 알림이 15분 내 담당자 확인(Ack)
   없이 미조치 상태로 남아있으면 2차 수신자(팀 리더 등)에게 SMS를 추가
   발송한다.

## 5. OS 메트릭별 상세 모니터링 기준

### 5.1 CPU

| 메트릭 | 임계치 | 판단 방식 | 유형 | 알림 등급(기본) |
|---|---|---|---|---|
| CPU Usage | ≥ 80%, 15분 지속 | 순간 Spike 제외, 이동평균 기준 | 성능저하형 | C |
| Load Average (Linux) | CPU Core 수 × 1.0 초과, 15분 지속 | `/proc/loadavg` 1분값 기준 | 성능저하형 | D |

### 5.2 Memory

| 메트릭 | 임계치 | 판단 방식 | 유형 | 알림 등급(기본) |
|---|---|---|---|---|
| Memory Usage | ≥ 85%, 15분 지속 | Available 기준 산출 권장 | 성능저하형 | C |
| Available Memory | < 15% | `MemAvailable` 기준 | 성능저하형 | C |
| Swap Usage | ≥ 70% | 사용률 단독 판단 금지(아래 비고) | 성능저하형 | D |

> 비고: Swap은 사용률만으로 장애를 단정하지 않는다. Swap Usage 임계치 초과가
> **Page/Swap Activity(초당 in/out) 지속 증가**와 함께 나타날 때만 실질적인
> 메모리 부족 징후로 판단한다.

### 5.3 Disk (물리 디스크/I/O)

| 메트릭 | 임계치 | 판단 방식 | 유형 | 알림 등급(기본) |
|---|---|---|---|---|
| Disk Latency | ≥ 20~30ms 지속 | 스토리지 종류(HDD/SSD/SAN)별 보정 필요 | 성능저하형 | D |
| I/O Error | 발생 시 즉시 | 장애 징후로 간주, 발생 자체가 트리거 | 성능저하형 | C |

### 5.4 File System

| 메트릭 | 임계치 | 판단 방식 | 유형 | 알림 등급(기본) |
|---|---|---|---|---|
| Disk(파티션) Usage | ≥ 80% | `/`, `/var`, `C:` 등 핵심 마운트 우선 | 성능저하형 | C |
| Inode Usage | ≥ 80% | Linux 전용 | 성능저하형 | D |
| Read Only 전환 | RO 전환 발생 | 완전장애형(쓰기 불가) | 완전장애형 | C |

### 5.5 Ping Fail (가용성/Host Alive)

| 메트릭 | 임계치 | 판단 방식 | 유형 | 알림 등급(기본) |
|---|---|---|---|---|
| Host Alive | 3~5분 응답 없음 | 모니터링 서버 → 대상 ICMP 연속 실패 | 완전장애형 | C (최우선) |

> 최초 1회 실패만으로 알림을 발생시키지 않고, 네트워크 순간 지연/패킷 유실과
> 구분하기 위해 **연속 실패(3~5분)**를 조건으로 한다.

### 5.6 Hang (시스템 응답 없음)

`BBT-요건` 원문에는 별도 행이 없어 아래와 같이 탐지 기준을 신규 정의한다.

| 판단 근거 | 임계치/조건 | 알림 등급(기본) |
|---|---|---|
| 커널 Hung Task 탐지 | 커널 로그에 "task blocked for more than N seconds" 발생 | C |
| Soft Lockup | 커널 로그에 "soft lockup - CPU#N stuck" 발생 | C |
| D-state(Uninterruptible) 프로세스 급증 | `ps -eo stat` 기준 D-state 프로세스 수, 평시 대비 지속 증가 | D |
| 모니터링 Agent 응답 없음 | 프로세스는 살아있으나(Host Alive는 응답) 커맨드 실행 결과 미수신 지속 | C |

> Hang은 "완전 다운(Ping Fail)"과 달리 **네트워크는 응답하지만 실질적인
> 명령 처리가 되지 않는 상태**를 의미한다. 따라서 Ping Fail 판정 로직과는
> 별도로, Agent의 커맨드 응답 여부 및 커널 로그를 함께 봐야 한다.

### 5.7 OS 커널 오류

| 메트릭 | 임계치 | 판단 방식 | 유형 | 알림 등급(기본) |
|---|---|---|---|---|
| Kernel Panic | 발생 시 즉시 | Linux 전용, 완전장애형 | 완전장애형 | C |
| Kernel Oops / General Protection Fault | 발생 시 즉시 | 즉시 패닉은 아니나 커널 불안정 징후 | 성능저하형 | C |
| Filesystem Error(커널 레벨) | 발생 시 즉시 | ext4/xfs 등, "5.4 File System"과 연동 | 성능저하형 | C |
| 비계획 System Reboot | 발생 시 즉시 | 계획된 점검/작업 일정과 대조 후 판단 | 성능저하형 | C |

> Windows의 BSOD/BugCheck는 이벤트 로그(Event Viewer) 기반으로 별도
> 관리하며, 본 문서의 6장(로그 문구)은 Linux `/var/log` 기준으로 작성했다.

## 6. `/var/log` 로그 기반 탐지 문구

### 6.1 대상 로그 파일

| 로그 파일 | 배포판 | 주요 용도 |
|---|---|---|
| `/var/log/messages` | RHEL 계열(8/9) | 시스템 전반 로그(커널 포함) |
| `/var/log/syslog` | Ubuntu 계열 | 시스템 전반 로그(커널 포함) |
| `/var/log/kern.log` | Ubuntu 계열 | 커널 로그 전용(있는 경우) |
| `dmesg` / `journalctl -k` | 공통(systemd) | 커널 링버퍼 직접 조회, 재부팅 시 초기화됨에 유의 |
| `/var/log/secure` (RHEL) / `/var/log/auth.log` (Ubuntu) | 공통 | 인증/권한 관련(참고용) |

> `syslog` 심각도(priority)를 지원하는 수집기라면 문자열 grep 대신
> **facility=kern, severity ≤ crit(2)** 조건으로 필터링하는 것이 더 정확하다.
> 문자열 기반 grep은 아래와 같이 보조 수단으로 사용한다.

### 6.2 항목별 grep 탐지 문구

| 분류 | 탐지 문구(대소문자 무관 grep 권장) | 연관 알림 등급 |
|---|---|---|
| 공통 심각도 키워드 | `critical`, `crit`, `emerg`, `panic`, `fatal` | 문맥에 따라 A~C |
| Kernel Panic | `Kernel panic - not syncing` | C |
| Kernel Oops | `Oops:`, `general protection fault`, `unable to handle kernel` | C |
| Soft Lockup / Hang | `soft lockup`, `blocked for more than`, `hung_task` | C |
| OOM(메모리 부족) | `Out of memory`, `oom-killer`, `Killed process` | C |
| 디스크 I/O 오류 | `I/O error`, `Buffer I/O error`, `critical medium error` | C |
| 파일시스템 오류 | `EXT4-fs error`, `XFS internal error`, `Remounting filesystem read-only` | C |
| 네트워크 인터페이스 | `NIC Link is Down`, `Link is Down`, `carrier lost` | C |
| systemd 서비스 실패 | `Failed to start`, `entered failed state` | C/D |
| 시간 동기화 | `ntpd.*no server suitable`, `chronyd.*Can't synchronise` | D |

> 위 문구는 시작점이며, 실제 배포판/커널 버전에 따라 메시지 표기가 달라질 수
> 있으므로 적용 전 대상 서버에서 `dmesg`/`journalctl` 실 사례로 1차 검증할
> 것을 권장한다.

## 7. 적용 시 참고사항

1. 메트릭 임계치(80%, 85% 등)는 **초기값**이며, 서비스 특성상 오탐이 잦은
   호스트는 개별 조정한다(예: 배치 서버의 CPU 100% 순간 사용은 정상).
2. 알림 등급과 통보 채널 매핑(4장)은 팀 운영 정책에 따라 조정 가능한
   **권장안**이다. 최종 확정 전 담당 조직과 합의가 필요하다.
3. 로그 기반 탐지(6장)는 메트릭 기반 탐지의 **보완 수단**이다. 동일 장애가
   메트릭과 로그 양쪽에서 동시에 잡히는 경우, 알림 중복 발송을 막기 위한
   dedup(중복 제거) 로직이 필요하다.
